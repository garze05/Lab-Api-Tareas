# Auditoría del workflow de despliegue

| Línea | Problema | Riesgo concreto | Corrección propuesta |
|---|---|---|---|
| `despliegue.yml:4` | Cualquier push inicia un despliegue, sin limitar la rama. | Una rama de pruebas podría terminar desplegada sin pasar por la revisión del equipo. | Desplegar solo con pushes a `main` y proteger esa rama. |
| `despliegue.yml:5, 16-18` | `pull_request_target` ejecuta el workflow con el contexto del repositorio base, pero el checkout trae código del pull request. Después se construye ese código. | Una persona que abra un PR podría modificar el Dockerfile para ejecutar comandos y acceder a los recursos disponibles durante la ejecución. | Quitar `pull_request_target` del despliegue. Revisar los PR con otro workflow de permisos mínimos y sin secretos. |
| `despliegue.yml:7` | Se usa `permissions: write-all`. | Si un paso o acción se compromete, puede usar el token para modificar recursos del repositorio, como el código o los paquetes. | Dar solo `contents: read`, que es lo que necesita el checkout de este ejemplo. |
| `despliegue.yml:9-10` | El token de staging está escrito en el workflow. | Cualquiera con acceso al repositorio o a su historial puede copiarlo y usar la API con ese token. | Invalidar y reemplazar el token; guardar el nuevo como secreto `API_TOKEN` del environment de GitHub. |
| `despliegue.yml:16` | La acción de checkout apunta a `main`, una referencia que puede cambiar. | Si cambia el código al que apunta, el workflow podría ejecutar una versión distinta o comprometida. | Fijar la acción a un SHA completo de una versión revisada. |
| `despliegue.yml:18` | La referencia del checkout depende del SHA del PR, que no existe en un evento `push`. | En un push no se selecciona de forma explícita el commit del evento; además, en un PR se trae código que aún no es confiable. | Para el despliegue por push, usar el checkout normal del commit que disparó la ejecución. |
| `despliegue.yml:20-25` | El paso de depuración activa `set -x`, imprime el token de GitHub, transforma el token de la API en base64 y muestra todas las variables. | Los logs pueden revelar credenciales. El enmascaramiento de GitHub no garantiza que se oculte un secreto transformado, como el codificado en base64. | Eliminar el paso. Si hace falta comprobar la configuración, mostrar únicamente si el token está configurado, sin imprimir su valor. |
| `despliegue.yml:29` | El título del PR se inserta directamente en un comando de shell. | Una persona que controle el título podría introducir comandos que se ejecuten en el runner y aprovechar sus permisos o secretos. | En este despliegue no hace falta el título, así que se elimina el paso. Si se necesita en otro workflow, pasarlo mediante una variable de entorno y citarla en el shell. |
| `despliegue.yml:35` y `.env:1-2` | Se usa un `.env` del repositorio con configuración de producción y un token guardado en texto plano. | El token de producción queda expuesto a quienes puedan leer el archivo o su historial; además, podría usarse producción en un despliegue equivocado. | Retirar `.env` del repositorio y evitar volver a agregarlo; invalidar y reemplazar el token. Definir `APP_ENV` y `API_TOKEN` en el environment correspondiente y pasarlos al contenedor al arrancar. |
